## 0. 术语

口述中「对话」「话题」「标签」三个词混用，但它们在产品模型里是三样不同的东西。先统一语言。

| 术语 | 定义 | 易混淆点 |
|---|---|---|
| **会话** Session | 用户发起的完整交互单元，在前端占一个标签，有独立生命周期 | 口述称「一轮对话」。本文一律用「会话」，「轮」留给轮次 |
| **轮次** Turn | 会话内的一次用户输入 + Agent 响应 | |
| **聊天记录** Transcript | 会话内全部轮次的完整留存，可回看 | 与图谱分离：会话消亡时记录一起消亡，图谱不受影响 |
| **话题** Topic | 从轮次内容中抽取出的技术课题，如「AI Agent 开发」 | 与会话是**多对多**：一个会话可涉及多个话题（下钻），一个话题可被多个会话复用（缓存命中） |
| **图谱** Atlas | 针对一个话题生成的结构化知识网络（节点 + 关系） | 一个话题可有多张图谱；图谱**不随会话消亡** |
| **子图** Sub-atlas | 由某个节点下钻生成的、以该节点为中心的新图谱 | 属于原话题的延伸，不是新话题 |
| **信源** Source | 被配置为定期采集对象的外部站点（科技公司官网、顶刊等） | 与「信息来源」区分：信源是定期采集的固定对象，信息来源还包括用户临时提交的文档与链接 |
| **知识库** Knowledge Base | 后端持久化存储，**仅存外部来源的知识片段**（用户上传文档、用户提交链接、周期采集）。它的存在意义是补充 LLM 内知识 | 口述称「RAG」。RAG 只是其中一种检索技术，故用更中性的「知识库」。**LLM 生成的任何内容都不进入知识库**——见「图谱缓存」 |
| **图谱缓存** Atlas Cache | 话题 → 图谱成品的持久化存储，供热路径直接复用 | 与知识库是**两个独立存储**，分开索引、分开管理。二者混为一谈会让 LLM 输出污染知识库的语义检索 |
| **新知识** | 知识库中相对 LLM 内知识构成补充的条目 | 判据不是「时间新」而是「LLM 是否掌握」，见 D-05 |
| **知识标签** | 附着在知识条目上的**技术名词**（如 `RAG`），入库时由 LLM 提取 | **不是话题**——话题粒度太粗且表述不稳定，用它做标签会让检索两端无法对齐。见 §3.5.3 |
| **词汇鸿沟** | 话题与相关知识在字面上不像，导致语义检索召回不到 | 例：「AI Agent 开发」与「RAG 新突破」技术强相关，但文本相似度低 |
| **守卫** Guardrail | 对输入做边界判定 + 内容提取标准化的模块 | |

**为什么必须区分会话与话题**：两者的生命周期**完全不同且必须解耦**——会话是交互记录，价值有限、短命（24h / 7d）；话题与图谱是可复用资源，保留 15 天。这个区分是 v2 最核心的一处修正。详见 §2。

## 1. 产品定位与目标

**定位**：AI 驱动的技术图谱生成器。用户描述想了解的技术方向，得到一张结构化、可交互、可下钻的技术全景图谱。

### 1.1 首要价值：第一时间了解技术领域的最新发展动态

对科技创新工作者而言，**只有第一时间了解最新的科技突破，才能及时利用这些突破开发新产品、新功能，从而创造价值、占领市场**。了解某个技术领域的最新发展动态，是本产品的首要价值。

**这也是本产品相对「直接询问 LLM」的不可替代之处**：LLM 的内知识有训练截止日期，天然滞后，「这个领域最近发生了什么」正是它答不准的那类问题——而这个问题恰恰是科技创新工作者最需要的。

**这条定位反向确证了定期采集（FR-SRC）的必要性**：采集不是辅助功能，而是产品的立身之本。没有采集，本产品相对直接问 LLM 就没有不可替代的价值。它同时把 D-05 从一条存储策略**升级为产品定义**——知识库存的就是「LLM 不掌握的内容」，这不是优化选择，而是产品成立的前提。

### 1.2 次要价值：技术全景与学习路线

新手不知道某项技术由哪些部分组成、涉及哪些技术、该按什么路线学习。产品把这个问题变成一张可看的图。

这个作用有价值，但**不够硬核**——直接询问 LLM 也能得到差不多的答案（虽然不直观）。它是产品的入口体验与承载形态，不是护城河。

### 1.3 核心目标

> 在保证回答质量的情况下，尽可能少地消耗资源并减少响应时间。

这条是**贯穿全篇的优化目标**，FR-KB 与 FR-SRC 两组需求都在为它服务。

**但它与 1.1 存在张力，需要在实现中显式处理**：资源效率优化的对象应当是「非时效性」的部分。**最新动态这条价值线不能为省 token 让路**——省掉它就等于省掉产品本身。如果不把这层优先级写明，「最小化资源消耗」会被无差别地应用到所有路径上，包括那条唯一不可替代的路径。

## 2. 生命周期模型

v1 曾把会话与图谱的生命周期绑在一起（产出图谱的会话留 30 天）。v2 判定这是错的，两者必须解耦。

**v1 的错误**：把「会话该留多久」（交互体验问题）和「图谱该保鲜多久」（知识时效问题）当成了同一个问题。

**v2 的模型**：会话按**交互价值**定寿，图谱按**知识时效**定寿，各自独立。

### 2.1 三条独立的时间线

| 实体 | 期限 | 计时基准 | 到期行为 |
|---|---|---|---|
| **会话**（未产出图谱） | 24 小时 | 最后活动时间 | 连同聊天记录一起消亡 |
| **会话**（产出过图谱） | **7 天** | 最后活动时间 | 连同聊天记录一起消亡 |
| **话题记录 + 图谱条目** | **15 天** | 生成时间 | 不因会话消亡而删除；到期一并清理 |
| **图谱的可复用性** | **15 天** | 生成时间 | 过期后不再直接复用，下次查询时重新生成 |

### 2.2 两个关键机制

**会话升档（单向上调）**：会话一旦成功产出图谱，即从 24h 档升入 7d 档，并重新计时。

- 24h：给用户一个「想起来还能回来接着问」的窗口。没产出图谱的会话是失败的尝试，不值得多留。
- 7d：产出过图谱说明这个会话有继续交流的可能（用户会回来追问、下钻），所以给更长窗口。**7 天对应的是交互连续性，不是图谱的复用价值**——图谱的价值已经由下一条机制独立承接了。

**图谱新鲜度（可复用性到期）**：图谱保留 **15 天**，超过后不再直接复用，下次遇到同一话题时重新生成。

- 复用的判据是**时间**，单一条件。新知识的触达由图谱之外的**通知栏**承担（§3.7），不再让图谱去追新知识。
- 15 天是与通知栏配合的结果：库里 3 天前到了新进展时，用户通过通知栏立刻就能看到，**不必为此重生成整张图谱**。于是图谱的滞后上界是 15 天，而知识触达是实时的——两者各司其职。
- **保留期与新鲜期是同一个 15 天**（D-24）。v7 曾把「存在」与「可复用」分成两个状态，但 D-13（全量重生成）与 D-16（旧图谱不参与）确立后，过期图谱既不会被返回也不会被参考——**没有任何消费者**，分成两个状态就没有意义了。
- **图谱缓存自身也会增长**（每个被查询过的话题一条）。D-23/D-24 判定其复用价值随新鲜期结束而归零，因此**保留期与新鲜期一致，都是 15 天**，到期直接清理，不做任何淘汰算法。
- 更新方式为**全量重生成后替换**（D-13）。旧图谱内容的处置见 D-16。

### 2.3 领域模型

```
用户
 └── 会话 Session ─────────────── 前端一个标签 + 一条聊天记录
      │                            生命周期：24h / 7d，到期整体消亡
      ├── 轮次 Turn 1
      ├── 轮次 Turn 2
      └── 话题 Topic
           └── 图谱 Atlas ───────── 生命周期：15 天，到期与话题记录一并清理
                └── 子图 Sub-atlas（由节点下钻产生）

知识库 Knowledge Base ──────────── 仅存外部来源，1 年硬删除期
 └── 知识片段（带技术名词标签）───→ 冷路径的检索上下文

图谱缓存 Atlas Cache ───────────── 15 天，按时间清理，不做淘汰算法
 └── 话题 → 图谱成品 ────────────→ 热路径直接返回
```

**两个存储都不随会话消亡**：这是资源优化目标的落点。用户 A 的会话 7 天后消失了，但他问过的「向量数据库」图谱仍会在缓存里留到第 15 天——用户 B 在这期间问同一话题可直接命中；15 天后则重新生成，而知识库里的外部知识仍会被检索到。

### 2.4 「演进」的落点

项目的核心主张是 dynamically evolving。在本模型下，**演进发生在知识库层，图谱是按需生成的快照，而新知识的触达由通知栏承担**：

- 知识库通过定期采集（FR-SRC）自主增长，不依赖用户查询
- 图谱在用户查询时基于当时的库内容生成，15 天后过期重生成
- 新知识的触达**不等图谱**——通知栏实时列出近期入库的知识（§3.7）

三者结合的效果是：**用户看到的图谱不超过 15 天，而新知识是实时可见的**，同时无需任何后台任务主动更新图谱。

这也回答了一个看似存在的缺口——「冷门话题永远不更新」。它不是问题：**没有人查看的图谱不需要保持新鲜**。真正需要保持新鲜的是知识库，而它由采集任务持续维护。演进的主体是库，不是图。

## 3. 功能需求

优先级：**P0** 核心必须 ｜ **P1** 应该实现 ｜ **P2** 可延后

### 3.1 FR-SESS · 会话生命周期

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-SESS-01 | 用户首次输入即创建会话，前端以标签形式呈现 | P0 |
| FR-SESS-02 | 会话可连续接收多轮输入。**单轮越界不中断会话**——仅返回提示，允许用户继续优化输入 | P0 |
| FR-SESS-03 | 匿名会话 ID：前端生成并持久化，随请求携带，后端据此关联 | P0 |
| FR-SESS-04 | 生命周期分层：未产出图谱 24h；产出过图谱 7d。时长可配置 | P0 |
| FR-SESS-05 | 计时基准为**最后一次活动时间**，而非创建时间 | P0 |
| FR-SESS-06 | 生命周期**单向上调**：首次成功产出图谱时从 24h 档升入 7d 档，重新计时 | P0 |
| FR-SESS-07 | 前端标签的保留状态与后端记录同步（清除后标签消失） | P0 |
| FR-SESS-08 | **完整持久化聊天记录**：会话内每个轮次的用户输入与 Agent 响应全量留存，支持回看 | P0 |
| FR-SESS-09 | 会话消亡时，聊天记录一并清除，**不级联删除话题与图谱** | P0 |
| FR-SESS-10 | 用户可手动结束或删除会话 | P1 |

**FR-SESS-09 是 v2 新增的边界约束**：会话到期清理时，必须只清会话与聊天记录，绝不触碰知识库。这条如果不写死，实现时一个 `ON DELETE CASCADE` 就会把长期积累的图谱一起带走。

### 3.2 FR-GUARD · 守卫模块

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-GUARD-01 | 边界判定，规则见 [01-topic-boundary.md](01-topic-boundary.md) | P0 |
| FR-GUARD-02 | 越界响应为**提示性回答 + 引导优化下一次输入**，不中断会话、不报错 | P0 |
| FR-GUARD-03 | 内容提取与标准化：把合格输入转为后续模块可直接使用的规范形式 | P0 |
| FR-GUARD-04 | **话题同一性判定**：接收新话题与候选历史话题，返回二者是否为同一话题 | P0 |
| FR-GUARD-05 | 一次调用同时产出「课题 + 意图 + 裁定」（见 01 §7） | P0 |
| FR-GUARD-06 | 判定结果可解释，拒答须说明理由并给示例 | P1 |

**FR-GUARD-03 的设计理由**（口述原文）：合格输入之间仍有巨大差异。用户可能说「AI Agent 咋学啊」也可能说「请系统梳理 AI Agent 开发涉及的架构模式、工具链与前沿方向」。两者都合格，但直接塞进生成提示词，输出质量方差会很大。守卫把它们**归一到同一形态**，给生成链路一个稳定的输入分布。

| FR-LLM-04 | **厂商结构化输出能力差异的归一** | P0 | ⚠️ 部分 |
| FR-LLM-05 | 流式生成 | P0 | ✅ 已实现 |
| FR-LLM-06 | 一次性返回接口本期保留，不删除 | P0 | ✅ 已实现 |

**FR-LLM-01～03、05 已由现有代码满足**，无需重新开发。依据：

- [services/llm/base.py](../../backend/services/llm/base.py) — `BaseLLMService` 抽象 + `LLMResponse` 统一结构
- [services/llm/factory.py](../../backend/services/llm/factory.py) — 零厂商硬编码的注册中心
- [services/llm/deepseek.py](../../backend/services/llm/deepseek.py) — 唯一知道厂商参数的地方

**FR-LLM-04 是真正的新增项**。各厂商差异实际存在于三层：

| 层次 | 差异 | 现有处理 |
|---|---|---|
| 调用参数 | DeepSeek 的 JSON 模式必须同时设 `max_tokens`；OpenAI 有 `json_schema` 严格模式 | 适配器内部吸收 ✅ |
| 输出保证强度 | 「保证合法 JSON」vs「大概率是 JSON」vs「需靠提示词引导」 | **未处理** ⚠️ |
| 截断语义 | `finish_reason` 取值不同 | 已归一为 `LLMTruncatedError` ✅ |

中间那层是缺口：下游无法假设所有 provider 都返回合法 JSON。当前实现的对策是「统一当文本处理 + Pydantic 兜底校验」，**此约定应成为规格而非隐含在代码里**。

### 3.4 FR-ATLAS · 图谱生成与结构

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-ATLAS-01 | LLM 输出的图谱须符合既定结构，便于前端渲染 | P0 |
| FR-ATLAS-02 | 图谱维度可扩展：当前为二维，**为三维及其它形态保留扩展能力** | P0 |
| FR-ATLAS-03 | 后端图谱数据结构与前端渲染能力**双向**可扩展 | P0 |
| FR-ATLAS-04 | 增量流式渲染（节点边生成边画） | P0 ✅ 已实现 |
| FR-ATLAS-05 | 图谱与话题、会话建立关联 | P0 |
| FR-ATLAS-06 | 图谱不随会话消亡（FR-SESS-09）；自身保留 **15 天**（D-24） | P0 |
| FR-ATLAS-07 | 图谱新鲜度：超过 **15 天**后不再直接复用（判据单一，见 §2.2） | P0 |
| FR-ATLAS-08 | 节点下钻：生成以该节点为中心的子图 | P1 |

**FR-ATLAS-02/03 的关键约束**：口述说「不确定是否存在三维图谱需求，但要保留可扩展性」。这意味着**不能把「二维」写进数据契约**——节点坐标不应由后端下发（下发即等于承诺了维度），布局应由前端渲染层负责。当前 [frontend/package.json](../../frontend/package.json) 用 `@dagrejs/dagre` + `@xyflow/react`，布局确实在前端，这个边界是对的，需**显式记录为约定**。

### 3.5 FR-KB · 知识库、图谱缓存与检索

本期**资源消耗优化目标的主战场**。

#### 3.5.1 两个存储，各司其职

口述曾把它们统称为「RAG 存储」，但它们是**两个性质完全不同的存储**，必须分开：

| | **知识库** | **图谱缓存** |
|---|---|---|
| 存什么 | 外部来源的知识片段 | 话题 → 图谱成品 |
| 来源 | 用户上传文档、用户提交链接、周期采集 | LLM 生成 |
| 用途 | 冷路径的生成上下文 | 热路径直接返回 |
| 检索方式 | 按**标签 + 语义**相关 | 按**话题**相似度 |
| 更新频率 | 高频，随采集持续追加 | 低频，15 天重生成一次 |
| 增长上界 | 无，需瘦身（§3.5.4） | 每话题一条，需淘汰（§3.5.4） |
| 膨胀风险 | **高** | 中 |

**LLM 生成的任何内容都不进入知识库。** 知识库的价值在于补充 LLM 不掌握的知识；把 LLM 的输出放进去，等于用已知信息稀释未知信息——既膨胀存储，又拉低检索精度（§3.5.5）。图谱成品存的是**图谱缓存**——那是缓存，不是知识。

#### 3.5.3 检索流程

口述指出了一处关键缺陷，并给出了正确解法：

> 比如话题是「AI Agent 开发」，知识库里有一条关于 RAG 的新知识，我感觉应该检索不到——因为检索技术不知道「AI Agent 开发」跟 RAG 之间存在关联。

**这是「词汇鸿沟」（§0 术语）。** 语义检索只能匹配文本相似度，而话题与它的相关知识在字面上常常不像。**破解办法是用 LLM 补上这层关联**——LLM 知道「AI Agent 开发」涉及 RAG、记忆机制、工具调用，这正是 embedding 没有的知识。

完整流程：

```
有效话题
   ↓ ① 查询扩展：LLM 生成该话题的相关技术名词（只是词汇，开销有限）
技术名词 [RAG, 记忆机制, 工具调用, ...]
   ↓ ② 用这些名词去知识库检索（标签匹配 + 语义检索）
相关知识片段
   ↓ ③ 话题 + 检索到的知识 → LLM 生成图谱
图谱
```

**① 与入库标签（FR-KB-09）必须使用同一类词汇，且标签是「技术名词」而非「话题」。**

产品负责人对此有明确要求：关于 RAG 的知识条目，标签就是 `RAG`，**不是「AI Agent 开发」这个话题**。两者不可混用：

| | 技术名词（✅ 用作标签） | 话题（❌ 不可用作标签） |
|---|---|---|
| 粒度 | 细，领域内的标准术语 | 粗，一次探索的入口 |
| 表达稳定性 | 高——`RAG` 就是 `RAG` | 低——同一个人两次可能说成「AI Agent 开发」「AI Agent 技术」 |
| 归属 | 属于知识本身 | 属于用户查询 |
| 基数 | 一条知识可有多个名词标签 | 相关话题的数量不受控 |

**若用话题做标签，两端必然对不齐**——入库侧的话题表述与检索侧生成的话题表述不会一致，匹配随即失效。**这是标签体系能否奏效的前提条件。**

**一个现实风险：同义词。** 入库时 LLM 打 `RAG`，检索时可能生成「检索增强生成」，字符串匹配就失效了。两个解法：标签也用**向量匹配**（单个术语的 embedding 比整篇文章聚焦得多，不受背景稀释），或维护一份**规范术语表**。前者省事，后者精确；具体选型留给架构设计。

**② 是「标签匹配 + 语义检索」的混合**，不是纯语义——标签是绕过词汇鸿沟的捷径。

#### 3.5.4 知识库瘦身与图谱缓存保留

**瘦身的目的不是省存储，是保检索精度**（论证见 §3.5.5）。库中若大量充斥着 LLM 已知的旧知识，检索的 top-k 会被它们占满，**真正的新知识反而排不进去**。

**机制（D-22）**：**时间衰减加权**——按入库时间降低检索排序权重，让新条目天然占优；外加一条 **1 年硬删除期**，条目在库中存续满 1 年即彻底删除。

**为什么时间衰减不是启发式，而是有物理含义的**（产品负责人的论证）：LLM 持续用新数据训练，今天的「新知识」终将成为明天的「内知识」。一旦被 LLM 掌握，它就不再是补充，而是冗余。**所以知识库天然有一个过期时间，约等于 LLM 的训练滞后周期。** 衰减反映的是「这条知识被 LLM 吸收的概率在上升」，而不是「旧的不受欢迎」。

这个论证比「让新知识在检索中胜出」更根本——后者是竞争性理由，前者是本体论理由。

**两点补充**：

1. **小众知识可能永远不进训练数据。** LLM 的训练数据覆盖不均匀：热门领域吸收快，小众细分领域可能长期不被覆盖——而 D-05 恰恰把「小众细分领域」列为知识库该存的内容。对这类条目，1 年硬删会删掉 LLM 仍未掌握的知识。

   **但这不需要为此改设计**：这类条目的来源是稳定信源，被删后下次采集能重新拿回。损失可恢复，知道有这个边界即可。

2. **LLM 自评可用于校准 1 年这个数字。** 口述原提的机制（让 LLM 指出它已经知道哪些）作为**单条删除依据**不可靠——模型对自身知识边界的校准很差，它说「知道」可能只是知道个大概，而版本号、具体参数这类细节恰恰是知识库最该补的。但作为**统计指标**它是可信的：单条判断会错，「过去 6 个月入库的条目中 LLM 自评已知的比例」这个趋势不会错。

   记录这个比例即可观测知识被 LLM 吸收的实际速度，从而校准 1 年这个期限。**这是把不可靠的单点判断，转化为可靠的趋势观测。** 建议保留自评记录，但只用于统计，不用于删除。

**图谱缓存与话题记录的保留（D-23 / D-24）**：**保留期 = 新鲜期 = 15 天，到期直接清理，不做任何淘汰算法。**

理由：图谱的复用价值**随 15 天新鲜期结束而归零**。超过 15 天不可复用，而重生成是全量的（D-13）、旧图谱不参与（D-16），所以一张过期图谱**没有任何消费者**——它既不会被返回，也不会被参考。**既然没有消费者，LRU / LFU 这类基于访问频次的策略就没有意义**，按时间淘汰即可。

**话题记录与图谱条目同生命周期（D-24）**：一张没有图谱的话题记录，唯一用途是相似度匹配（FR-KB-02），而匹配上了照样要重生成——价值接近零。让它长期留存，只是让库里累积无法被消费的条目。

#### 3.5.5 预处理为何必要：不只是省空间

口述提出疑问：

> 知识库中知识的精确性会不会影响到搜索话题的匹配度？……否则瘦身似乎只起到了一个节约存储空间的效果。

**答案是：会，而且影响很大。预处理与瘦身不只是省空间，是检索质量的前提。** 三个原因：

1. **embedding 是整段文本的平均语义。** 一篇文章若 80% 是背景介绍、20% 是新突破，它的向量会被背景主导——检索时匹配到的是「背景话题」，而不是那个新突破。只取新技术发展的部分，向量才指向真正的内容。

2. **粒度不匹配。** 一段 2000 字的文章与一个 10 字的话题查询，粒度严重失衡。**切分成聚焦的小段**（按主题切，而非按字数切）后，每段的向量才够锐利。这一条比「筛选」更关键——即便整篇都是新技术内容，不切分照样检索不准。

3. **信噪比决定 top-k 的可用性。** 向量检索取相似度最高的 k 条，库内低质内容越多，top-k 被稀释得越厉害。清洗是让有用片段挤进 top-k 的必要条件——**这与瘦身是同一个道理的两个方向**：一个管入库，一个管存量。

**结论：入库预处理（FR-KB-08/09）与知识库瘦身（FR-KB-11）都是检索精度的手段，节省存储只是顺带效果。** 口述的怀疑成立——如果它们只省空间，就不值得做；正因为它们决定检索质量，才必须做。

**优先级两度上调：P2 → P1 → P0**（01 / 02 / 03 三项）：

- **P2 → P1**：FR-KB-04 冷路径的价值完全依赖知识库里有内容，而知识库的填充只有 FR-SRC 这一条路径。没有采集，冷路径退化为「什么都检索不到，直接让 LLM 凭空生成」。
- **P1 → P0**：§1.1 把「了解最新发展动态」定为首要价值后，采集从「让冷路径更有料」升级为**产品立身之本**。FR-DYN-01 的数据源完全来自采集（见 §3.7），没有采集，首要价值线直接归零。

去重（04 / 05）与筛选（07）保持 P1——它们是质量优化，不是价值前提。用户提供信息源（06）是独立功能，保持 P1。

**FR-SRC-02 的采集策略**（口述原文）：不针对具体话题采集，而是广泛搜集科技前沿信息。目标是全球大型科技公司（电子产品 / AI / 生物科技等）的科研成果，以及 Nature、Science、IEEE 等顶刊发布的论文。信源清单由前端配置，采集任务只在这些信源上运行。

**FR-SRC-01 定位为运营后台功能，但本期不做权限控制**（D-17）。当前工具为初步版本、基本单人使用，接口开放无妨。**对外发布前必须补上**——采集源是全站共享资源，开放配置意味着任何访问者都能改变所有用户看到的图谱内容。

**这个转向的正面价值**：信源的领域（科技）与产品服务的领域（科技）重合，因此**「新信息与话题关联度」问题被大幅弱化**——用户问的任何话题都是科技话题，而库里存的都是科技前沿信息，二者天然处于同一语义空间。这是 v1 的 D-06 所担心的关联度问题在此转向下自然缓解的原因。

**但这个转向也转移了技术责任**：v1 建议的解法是「采集时主动建立与话题的关联」，现在采集不针对话题，关联只能在**检索时**做。责任从采集端移到了检索端——而 D-12 已把检索定为 best-effort、不设质量门槛，所以这项技术责任**被主动放弃了**，不是被解决了。

### 3.7 FR-DYN · 最新发展动态

承载 §1.1 的**首要价值**。

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR-DYN-01 | **通知栏**：列出近期（默认 15 天）入库的新知识，按时间倒序，最新在上。每条带知识标签（如 `RAG`）与入库时间 | P0 |
| FR-DYN-02 | **可查看原文**：点击通知条目可查看该知识的完整内容，**不必重新生成图谱** | P0 |
| FR-DYN-03 | **话题内动态**：查询某话题时，呈现与该话题相关的近期知识条目 | P0 |
| FR-DYN-04 | **空状态不得编造**：没有近期条目时明确说明「暂无近期动态」 | P0 |

#### 通知栏为何优于「触发重生成」

通知栏把**新知识触达**与**图谱更新**解耦，这是本轮设计的关键简化：

- 用户要的是「知道有新东西」，不是「图谱里多一个节点」。通知栏直接给前者；图谱重生成给的是后者，还要付一次 LLM 费用。
- 通知栏能带上**原文与来源**（FR-DYN-02），信息完整度高于图谱里的一个节点。
- 图谱因此回归单纯的「结构快照」，复用一个简单的 15 天规则就够，**不再需要判断「有没有值得重生成的新知识」**——原先的 D-20（门槛）与 D-21（反抖动窗口）随之双双消失。

这也顺带解决了之前的 D-19 困局：图谱与动态可以不一致，因为用户本来就从通知栏获取新知识，不会指望图谱承载它。

#### 为什么动态不能由图谱承载

图谱表达的是**结构**（这个技术由哪些部分组成），最新动态表达的是**时间**（最近发生了什么）。这是两个正交的维度。当前 `AtlasNode` 没有任何时间字段，四个 category 里最接近的 `frontier`（前沿发展）也是无时间戳的静态分类。

强行让图谱承载时效，只有两条路，**都不成立**：

| 做法 | 为什么不成立 |
|---|---|
| 图谱对比：与上一版 diff，高亮「新增节点」 | **图谱变化 ≠ 领域变化**。LLM 两次生成的节点差异，一部分是真实的新知识，一部分只是输出方差。把输出方差呈现为「最新动态」，是在用户最无法自行核实的价值线上误导他 |
| 给节点打时间戳 | `_parse_atlas` 拿到的只是模型输出的一段文本，模型无法可靠地知道某个节点「是哪天出现的」 |

#### 数据源

FR-DYN 的数据源是**知识库**，不是图谱缓存——知识条目天然带入库时间、来源与标签（D-14），这是通知栏需要的全部字段。

**FR-DYN-01 与 FR-DYN-03 是同一能力的两个视角**：通知栏是**全局**的（所有新入库的知识），话题内动态是**局部**的（当前话题相关的）。数据源相同，过滤条件不同。

#### 空状态为何必须显式禁止编造

这是 NFR-03「输出的不确定性防御」在时效场景下的具体化。知识库里确实没有新东西时，模型有很强的倾向去「补充」一些听起来很新的内容——那全是幻觉，而且恰好出现在用户最看重、也最无法自行核实的这条价值线上。**这是全产品最不能容忍幻觉的一处。**

| | `cross_domain_ideas` | FR-SYNTH |
|---|---|---|
| 输入 | 单个话题 | 两个或多个话题 |
| 输出 | 字符串列表，是当前图谱的一个属性 | 一次独立的生成任务 |
| 深度 | 浅层提示，一两句话 | 深层深挖 |
| 归属 | 属于已有图谱 | 产生新产物 |

前者维持现状，后者是新增。

#### 留位的具体要求

**1. 话题来源须可扩展。** 当前话题只有一个来源：用户输入经守卫提取。本需求要求话题还能来自「多个已有话题的组合」；而 FR-ATLAS-08 的下钻要求话题能来自「已有图谱中的一个节点」。

**这两者是同一类需求——从一个或多个已有图谱派生出新话题。** 架构应把「话题来源」抽象为一等概念，让下钻与碰撞共用一套机制。若各做一套，守卫判定、知识库检索、图谱关联这三处都要重复实现，且行为会随时间分叉。

**2. 图谱容器无需改动。** 产物已定为一张合成图谱，其话题标识形如「AI Agent × 生物科技」，仍是单值字符串——`AtlasResponse` 结构与前端渲染完全复用。

**3. 检索须支持多话题。** FR-KB-04 冷路径目前按单话题检索，碰撞需同时为多个话题检索并整合。

**4. 合成话题须与普通话题分开索引。** 理由见下，这是产物形态定案后浮现的一处副作用。

#### 产物形态

**已定为「一张合成话题的新图谱」**（D-18），话题标识形如「AI Agent × 生物科技」。

这个选择让**图谱层完全复用**：结构不变、生成链路不变、前端渲染不变。碰撞与普通生成的全部差异收敛到「话题从哪来」这一处——进一步印证了留位的核心是话题来源的抽象，而不是图谱容器的改造。

**但有一处副作用落在检索层：**

合成话题若与普通话题混在同一索引里参与相似度检索（FR-KB-02），会产生**错误命中**。库里同时存在「AI Agent」与「AI Agent × 生物科技」时，用户查询「AI Agent」可能检索到后者——因为它包含了前者的绝大部分语义。若守卫的同一性判定（FR-GUARD-04）没能拦下，用户会拿到一张融合图谱，而他要的是单一话题图谱。

对比 D-09 的下钻子图污染问题，合成话题更严重：**子图只与一个父话题相似，合成话题与它的每一个父话题都相似**，且父话题越多越容易误命中。

**建议**：话题带类型标识（单一话题 / 合成话题），相似度检索只在同类型内进行。这与「话题来源作为一等概念」的抽象方向天然一致——来源类型本来就要记录，只是多了一个用途。

## 6. 决策记录

### 6.1 已决

| 编号 | 问题 | 结论 |
|---|---|---|
| D-01 | 标签粒度 | **会话**。话题级复用作为后端机制，命中缓存时在当前会话内直接返回，不新建标签 |
| D-02 | 会话归属 | **匿名会话 ID**。前端生成并持久化，随请求携带。本期不做用户体系 |
| D-03 | 生命周期精确规则 | 见 §2 与 FR-SESS-04～07。计时基准为最后活动时间；软删除 + 延迟物理清理；升档判据为「至少一张图谱成功生成并返回」 |
| D-04 | 最终输出是否必须经 LLM | 拆两问：**从原始知识用纯代码组装图谱不可行**（分类与关系判定是语义任务）；**复用已生成的图谱成品可行**，即热路径 FR-KB-03 |
| D-05 | 知识库该存什么 | 存 LLM **大概率不掌握**的内容：外部新发布信息、用户上传的私有文档、小众细分领域。判据不是「时间新」而是「LLM 是否掌握」，后者无法预判，用上述启发式近似 |
| D-06 | 新信息与话题关联度 | **原问题作废**——采集策略已转向「广泛搜集科技前沿，不针对具体话题」（FR-SRC-02）。风险从采集端转移到检索端，见 D-12 |
| D-07 | 内容筛选是否必要 | **必要**，但目的是保精度不是省空间。向量检索质量依赖库内信噪比，低质内容会稀释 top-k 结果。筛选只在写入时做一次 |
| D-08 | 「不重复搜索同一处」如何界定 | 两层去重：**来源级**（URL 集合）+ **内容级**（近似重复检测）。内容级去重与 D-07 的筛选是同一处能力，合并实现 |
| D-09 | 下钻子图算不算新话题 | **不算**，是原话题的延伸。子图缓存挂在父话题下，按「父话题 + 节点 ID」索引，不独立成话题 |
| D-10 | 会话升级后越界轮次是否保留 | **已由生命周期重构消解**。会话整体消亡（24h / 7d），不做内容级裁剪 |
| D-11 | 无账号体系下的额度保护 | 会话内轮次上限 + 单 IP 每日会话数上限。越界请求不触发生成，只计成功生成。阈值待实测单次成本后确定 |
| D-12 | 检索端如何为话题找到相关信息 | **不设质量门槛**——理由：**检索失败不可观测**，无法区分「库里没有相关信息」与「检索没找到」，因此任何「查够了吗」的判断都缺乏基准。检索方法已由 §3.5.3 的「LLM 查询扩展 + 标签匹配」确定 |
| D-13 | 图谱更新语义 | **A 全量重生成 + 替换**。旧图谱内容的处置见 D-16 |
| D-14 | 信源可得性边界 | 只采集**元数据与摘要**（标题、摘要、作者、DOI、发布时间），不采集全文。顶刊有付费墙且涉及版权，但摘要足以让 LLM 知晓「有这么个新进展」，而知晓进展本身就是图谱更新的触发条件 |
| D-15 | 聊天记录存储与体量 | 按**轮次分页拉取**，不整段返回；图谱在记录中以**引用**形式存储，渲染时从知识库取最新版本，避免同一图谱在记录中存多份 |
| D-16 | 旧图谱内容是否归档 | **不归档**。被替换后直接丢弃，不提供回滚。副作用：「相比上次新增了哪些知识点」这类演进轨迹能力若将来需要，须单独立项 |
| D-17 | 信源配置的权限归属 | **运营后台功能**，但本期**不做权限控制**——工具为初步版本、基本单人使用。对外发布前必须补齐，见 §7 |
| D-18 | 碰撞的产物形态 | **一张合成话题的新图谱**（如「AI Agent × 生物科技」）。图谱层完全复用；副作用是合成话题须与普通话题**分开索引**，否则会误命中单一话题的查询，见 §3.9 |
| D-19 | 最新动态与图谱版本的一致性 | **由通知栏解决**（§3.7）——新知识触达与图谱更新解耦，图谱回归 15 天的单一保鲜规则。原「触发重生成」方案及其派生的 D-20（门槛）、D-21（反抖动窗口）一并作废 |
| D-22 | 知识库瘦身与删除 | **时间衰减加权 + 1 年硬删除期**。理由（产品负责人）：LLM 持续用新数据训练，今天的「新知识」终将成为明天的「内知识」，被掌握后就不再是补充而是冗余。**这使时间衰减从启发式变成有物理含义的机制**——衰减反映的是「被 LLM 吸收的概率在上升」。两条补充见 §3.5.4 |
| D-23 | 图谱缓存的保留期 | **保留期 = 新鲜期 = 15 天，不做任何淘汰算法**——复用价值随新鲜期结束而归零，重生成是全量的（D-13）、旧图谱不参与（D-16），过期图谱没有任何消费者，LRU / LFU 失去意义 |
| D-24 | 话题记录的生命周期 | **与图谱条目同生命周期，都是 15 天**。一张没有图谱的话题记录价值接近零——唯一用途是相似度匹配（FR-KB-02），而匹配上了照样要重生成。注：这与口述早期的「一直保留」不一致，属经确认后的修正 |

### 8.3 下一步

进入**架构设计**，产出系统分层、模块边界与接口契约。

架构设计需要重点回应的**五处**结构性问题：

1. **无状态转有状态**（§5）——当前后端不记录任何东西，而本规格几乎每项需求都要求状态。
2. **知识库与图谱缓存的分工**（§3.5.1、FR-KB-06）——两个存储分开索引、分开管理，且**知识库绝不接收 LLM 生成的任何内容**。这是知识库检索质量的前提，也是口述中「否则知识库会快速膨胀」顾虑的正面解答。
3. **可扩展性边界**（FR-ATLAS-02/03、FR-KB-10）——图谱维度、存储后端两个方向要预留扩展点，但不实现。
4. **话题来源的抽象**（§3.9）——下钻与碰撞同属「从已有图谱派生新话题」，须共用一套机制。话题需带**来源类型**（用户输入 / 图谱节点 / 多话题合成），该类型同时决定检索索引的分区（D-18）。这项留位本期就要做对，事后补装成本极高。
5. **检索链路的两段式结构**（§3.5.3）——冷路径从「话题 → 检索 → 生成」变成「话题 → LLM 查询扩展 → 检索 → 生成」，多了一次轻量 LLM 调用；同时知识入库需提取标签（FR-KB-09）。**两端的词表必须对齐**（入库标签用什么词，查询扩展就生成什么词），否则标签体系形同虚设。这是一条本期新增的独立链路。
