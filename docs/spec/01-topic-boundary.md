# 01 · 话题边界

> 状态：**已定稿** ｜ 定稿日期：2026-09-21
> 本文是话题准入判定的唯一真源。实现、提示词、测试用例若与本文冲突，以本文为准。

TechAtlas 接收什么样的课题。判定发生在**生成之前**，不过的输入不消耗生成额度。

---

## 0. 边界是三层，不是一个

| 层 | 判定内容 | 不过的后果 |
|---|---|---|
| **L1 话题** | 课题属不属于科技范畴 | 结构性不兼容——图谱 schema 填不出来 |
| **L2 意图** | 用户要的是不是"探索技术版图" | 话题对、产物错 |
| **L3 粒度** | 课题宽窄是否落在可成图区间 | 图能画，但要么空泛要么干瘪 |

三层独立判定，任一不过即不生成：

- 「帮我写篇 AI Agent 论文」→ L1 过、**L2 不过**
- 「数学」→ L1 过、L2 过、**L3 不过**
- 「中国历史」→ **L1 不过**

---

## 1. L1 · 话题边界：技术生态判据

### 判据

**该课题能否自然拆出 6–12 个节点，并让四类 category 都有意义？**

| category | 含义 | 判别力 |
|---|---|---|
| `core_concept` | 课题有内核 | 弱——几乎什么课题都有 |
| `sub_technology` | 有可独立命名的支撑技术 | 中 |
| **`tool`** | **有真实工具 / 框架 / 产品生态** | **强——决定性的一栏** |
| `frontier` | 有演进方向 | 中 |

**`tool` 是判别位。** 基础学科（数学、理论物理、纯理论）卡的都是这一栏。

没有工具生态的课题，模型只能**编造** `tool` 节点。幻觉比拒答更伤产品——用户拿到一张看起来完整、实则虚构的图谱，比收到一句「这个课题超出了我的范围」损失大得多。这是「硬拒」而非「软引导」的根本理由。

### 落点原则

基础学科的准入，**看课题的落脚点，不看学科归属**：

- 落点 = 理论体系本身 → 拒
- 落点 = 应用 / 工程 / 技术前置 → 收

**数学以「节点」身份进入图谱，不以「课题」身份。**

用户问「学 AI Agent 开发要什么基础」，`线性代数` 应当作为 `depends_on` 指向的前置节点出现在图里——这是产品最有价值的场景之一。而当用户把「线性代数」当成课题提交时，拒。

### 为什么不用学科清单

「限定在应用科学与科技」无法落成可执行的规则：

1. **学科无法穷举**，边缘案例无法枚举（数学算不算应用科学，在产品层面无解）
2. **同一个学科横跨两个判定**——数学既可能是越界课题，也可能是界内节点
3. 按学科清单判定会在边缘案例上**反复摇摆**：同一个课题今天拒、明天收

技术生态判据把「学科归属」这个无解的争论，换成了一个可测的问题：能不能填满四类节点。

## 2. L2 · 意图边界

从用户自然语言中**同时抽取课题与意图**，分别判定。

| 在界内 | 越界 |
|---|---|
| 探索技术版图 | 写代码 / 调试 |
| 了解学习路线 | 要具体结论或选型建议（「A 和 B 哪个好」） |
| 技术选型调研 | 写文档 / 论文 |
| 领域全景梳理 | 闲聊 / 纯事实查询 |

**意图越界 ≠ 话题越界。**「帮我写一篇 AI Agent 的论文」的话题完全在界内，被拒是因为意图。判定器必须能区分这两者——对同一个输入给出正确裁定但归错层，仍是错的（见 §5 的 `blocked_by`）。

---

## 3. L3 · 粒度边界

- **过宽**：拆不出清晰层次，四类节点都会退化成泛泛而谈（「科学」「计算机」「数学」「AI」）
- **过窄**：可独立命名的技术实体不足 6 个（某个具体 API、某个具体用法）

节点数区间 6–12 已由 [../../backend/prompts/atlas_system_prompt.md](../../backend/prompts/atlas_system_prompt.md) 的提示词约束，但那是**软约束**（schema 不校验）。L3 是把它提升为**准入门槛**。

---

## 4. 三种裁定与产品行为

| 裁定 | 值 | 触发 | 产品行为 |
|---|---|---|---|
| **准入** | `accept` | 三层全过 | 正常生成 |
| **硬拒** | `reject` | L1 结构性不兼容，或 L2 意图越界 | 明确拒答 + 说明边界 + 给 2–3 个示例课题 |
| **收窄建议** | `narrow` | L1、L2 过，但 L3 过宽 / 过窄 | **不生成**，反问用户想聚焦哪个方向 |

硬拒与收窄建议的分界线：

- **用户的想法是对的，只是没说清楚** → 收窄建议
- **用户想要的东西这个产品不做** → 硬拒

「收窄建议」不生成图谱。它的价值是把模糊输入转化成有效输入，而不是给一张平庸的图。

## 5. 验收案例集

机器可读版本：[../../backend/tests/fixtures/topic_boundary_cases.json](../../backend/tests/fixtures/topic_boundary_cases.json)

该文件同时是**需求枚举**与**判定器的测试用例表**。每条含 `verdict`（期望裁定）、`blocked_by`（在哪一层被拦）、`rationale`（期望理由）。

`blocked_by` 是刻意设计的断言位：判定器返回了正确裁定但归错层，说明它没真正理解边界，只是碰巧蒙对。

### 高判别力的对照对

以下是全表中信息量最大的两组，实现时优先跑通：

| 对照 | 裁定差异的根源 |
|---|---|
| 「线性代数」拒 ↔「机器学习中的线性代数」收 | 落点不同，学科相同 |
| 「量子力学」拒 ↔「量子计算」收 | 前者无工具生态，后者有 |

### 必须写死的边缘案例

「线性代数」「量子力学」「认知科学」「AI 伦理」这几条不写死，判定会在实现阶段来回摇摆。它们不是显而易见的越界项——用户会觉得这些课题很"科技"，所以它们恰恰是最需要固定答案的地方。

## 6. 待定灰区

以下情形本规格**尚未裁定**，实现时应标记为已知未覆盖，不要自行发挥：

| 灰区 | 问题 |
|---|---|
| 医学 / 农学 / 军事 | 是「应用学科」但不是「技术」。判据理论上适用（看能否填满四类节点），但未经案例验证 |
| 「XX 技术」中的 XX 为非科技领域 | 如「法律科技」「教育科技」——落点在技术还是在本领域？ |
| 课题是科技、但用户是研究者而非学习者 | 意图判定是否覆盖「找研究方向」这类诉求 |

填这些洞需要真实用户输入样本，不靠推演。先按 §5 跑通，灰区积累到足够样本后再回来补。

## 7. 实现约束（需求级）

1. **判定不能靠关键词枚举。** 这正是原先 `domain_guard.py` 的关键词方案被删除的原因（见 README「已知的后续工作」）。

2. **判定必须一次调用同时产出三项**：课题、意图、裁定（含 `blocked_by` 与收窄候选）。这决定的不是代码写法而是产品手感——多一次串行调用，就是生成前多 1–2 秒空白。

3. **`narrow` 裁定的收窄候选是建议不是选项**。给出 2–3 个方向供用户点选，但不排除用户自己重写课题。

4. **判定结果必须可解释。** 拒答要把理由说清楚并给示例，否则用户无法修正自己的输入。

> 判定器的输入输出契约、与生成链路的具体接线方式，属于**模块设计**阶段，不在本文范围。
